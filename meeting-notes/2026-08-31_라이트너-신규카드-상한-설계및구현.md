## 논의 주제
- 라이트너 알고리즘에 "단계별 카드 제한 개수"가 없어서, 오답이 쌓여도 신규 카드가 무제한으로 계속 유입될 수 있는 것 아니냐는 의문 제기.
- 이어서 이 개선을 설계 문서 → 코드 → DB까지 실제로 반영해달라는 요청.
- 마지막으로 Supabase 원격 DB에 직접 접근·수정할 수 있는 CLI 연결까지 셋업.

## 진단 / 발견사항
- 기존 설계(`newCap`, `dailyGoal`, `reviewCap`)는 "하루에 몇 개 신규로 유입할지"만 제한하고, 박스1~6에 누적된 **학습 중 카드 총량**에는 상한이 없었음.
- 오답이 쌓여 정체되면 매일 정해진 `newCap`만큼 계속 신규가 들어와 밀린 복습이 눈덩이처럼 불어날 수 있는 구조적 공백이 있었음.
- Supabase 프로젝트(`공부의 비결`, ref: `azayzkelmufcrjkivwdx`)는 이미 생성돼 있었고 `settings` 테이블에도 사용자 2행이 이미 존재 — 즉 로컬 `schema.sql`만 고쳐서는 실제 운영 DB에 반영되지 않는 상태였음.

## 결정 사항
- `maxActiveCards`(기본값 150)라는 새 파라미터를 도입해 박스1~6 누적 카드 수가 상한에 도달하면 신규 유입을 자동으로 0으로 막기로 함 (예방적 WIP cap).
- 신규 유입량 계산식을 `min(dailyGoal 여력, newCap, maxActiveCards 여력)`으로 변경.
- 설정 화면에 사용자가 `dailyGoal`/`reviewCap`/`newCap`/`maxActiveCards`를 직접 조정할 수 있는 UI(학습량 섹션)를 신설.
- Supabase 운영 DB 변경은 코드만으론 반영되지 않으므로, 실제 DB에 `alter table` 마이그레이션을 별도로 적용해야 함을 확인 및 실행.
- 앞으로 이런 DB 변경을 Claude가 직접 처리할 수 있도록 Supabase CLI를 로컬에 설치하고 로그인·프로젝트 연결(link)까지 완료.
